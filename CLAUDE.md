# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BBANGFishing is a Unity 6 (`6000.3.15f1`) fishing game using the Input System, Cinemachine, Unity Behavior (`com.unity.behavior`) and TextMesh Pro. It is a team project developed on per-member branches (`CHG`, `KU`, `NKT`, `JJK`, `Base`, merged into `main`). Code comments, tooltips and log messages are written in Korean; keep new ones consistent with that.

There is no CLI build, lint or test setup: `com.unity.test-framework` is installed but there are no test assemblies or tests, and no CI config. Compiling, running and testing all happen in the Unity Editor (scenes such as `Assets/Member/CHG/01.Scene/TestScene.unity` are used as sandboxes, driven by throwaway scripts in each member's `Test/` folder, e.g. `CHG/02.Script/Test/TestRod.cs` with its `[ContextMenu("Catch")]` that spawns a fish).

The latest fish/enemy-skill code lives on the `CHG` branch; `main` and `Base` may not contain `EnemySkillSystem`, `Projectile/` or `LungeModule` yet, so check the branch before concluding that something is missing. `*.csproj`/`.sln` files at the root are generated by Unity/Rider and should not be hand-edited.

## Layout and ownership

- `Assets/DevLib/` — shared, reusable systems, each in its own asmdef (ModuleSystem, SkillSystem, ObjectPool, SoundSystem, EventChannelSystem, AnimatorSystem, DatabaseSystem). **Shared across team members — don't modify these to suit one feature; layer new behavior on top from a member folder.** Namespaces are `DevLib.<System>`.
- `Assets/Member/<initials>/` — per-person work areas (`CHG`, `KU`, `NKT`). Stay inside the area you're working for. CHG code lives under `Assets/Member/CHG/02.Script/` with namespace `CHG._02.Script.<Folder>`; NKT uses `NKT.<Folder>`.
- Member scripts have **no asmdef** (they compile into `Assembly-CSharp`), so they can reference every DevLib assembly. DevLib asmdefs cannot reference member code, and `ModuleSystem`/`PoolRuntime` have no dependencies of their own — keep it that way.

## Architecture

### Module system (`DevLib/ModuleSystem`)
The core composition pattern. A `ModuleOwner` (e.g. `Agent` → `Fish`, NKT `Player`) collects every `IModule` found via `GetComponentsInChildren` in `Awake`, keys them **by concrete type** in a dictionary, then calls `Initialize(owner)` on all, then `IAfterInitModule.AfterInit()` on all.

- Only one module of each concrete type per owner (`ToDictionary` throws on duplicates); `GetModule<T>()` also resolves by interface/base type.
- `Initialize` order is not guaranteed: in `Initialize` only grab references (`owner.GetModule<X>()`); subscribe to other modules' events in `AfterInit`.
- Derive from `Module` for the `_owner` boilerplate, or implement `IModule` directly when a base class is already taken (the enemy skill modules do this).

### Combat (`CHG/02.Script/CombatSystem`)
- `IDamageable` + `DamageData` struct are the shared damage contract. `Agent` (`Agents/Agent.cs`) is the abstract `ModuleOwner` + `IDamageable` base with health and `OnDamaged`/`OnDeath` events; `Fish` extends it. Projectiles and bombs are also `IDamageable` so they can be shot down. `IParryable` (`IsParryable` + `TryParry(DamageData)`) is the parry contract; `Fish` implements it by delegating to `LungeModule`. `KnockbackModule` applies `DamageData.KnockbackPower` as an impulse on `OnDamaged` (`Fish` does its own weight-scaled version when `isKnockBack` is set — don't add both to the same fish).
- **Enemy skill system is CHG's own, separate from `DevLib/SkillSystem`** (which is player-oriented: `AbstractSkill`/`AbstractSkillModule`/`SkillDataSo`). Do not make `AbstractEnemySkill` inherit from it. Two layers:
  - *Execution* — `AbstractEnemySkill` (MonoBehaviour; runs `WarningTime` telegraph then the abstract `ExecuteSkill` coroutine, owns per-skill cooldown) driven by `EnemySkillModule` (one skill at a time, plus a module-level cooldown with per-skill `moduleCoolTimeOffset` / `ignoreModuleCoolTime`). Concrete skills are in `EnemySkillSystem/Skills/` (`Bomb`, `Dash`, `CurvedProjectile`, `StraightProjectile`, `Heal`; override `CanUseSkill` for extra use conditions, as `HealSkill` does); skills must be child objects of the module's GameObject and are keyed by `EnemySkillDataSO.SkillIdHash.HashValue` (must be unique per owner). `StopSkill()` is the forced end (e.g. a BT abort): it stops the coroutine, calls the `OnStopped()` hook (override it to undo side effects, as `DashSkill` does to cancel its horizontal velocity), then ends the skill normally (cooldown still starts). `DashSkill` needs a non-kinematic `Rigidbody` on the owner and moves it with `AddForce`, not by writing `transform.position`.
  - *Selection* — done by the Behavior graph (see Fish below); there is no code-side strategy layer (the old `AttackDecisionModule`/`ISkillStrategy`/`PrioritySkillStrategySO` were removed). `UseSkillAction` (`[Agent] use skill to [Target]`, shared by the fish and boss graphs) reads `FishDataSO.Skills` / `BossDataSO.Skills` through `ISkillEntrySource` (`SkillEntry[]`: a `Skill` hash, a `Priority` where higher runs first, and `AbstractSkillCondition[]` that must all pass), keeps the highest-priority entries that pass their conditions and `EnemySkillModule.CanUseSkill`, picks one at random and calls `UseSkill`. `AbstractSkillCondition` (ScriptableObject, `IsCanUse(SkillConditionContext)`) assets are shared by every fish that references them, so they must be stateless; add new conditions as new subclasses. Species differ by their `Skills` data and by which skill components sit on the prefab (a skill the fish lacks simply fails `CanUseSkill`); the graph itself is shared.
- Planned but not yet implemented: boss phases (try `HPBelowCondition` + `Priority` in `BossDataSO.Skills` first), a boss aura track running beside the main skill, and a boss-only `BossWeakPoint` interrupt that would call `CurrentSkill.StopSkill()` the way `PatternBreakModule` already does. Deliberately **not** adding weak-point fields to the shared `DamageData`.
- Skills are identified everywhere by `HashDataSO` (from `DevLib/AnimatorSystem`, a ScriptableObject wrapping `Animator.StringToHash`), used for both skill IDs and animator params.

### Object pooling (`DevLib/ObjectPool`)
`PoolManagerSO` holds `PoolItemSO` entries and is initialised at runtime by a scene `PoolInitializer` (singleton, `DontDestroyOnLoad`) — a scene without one will trip the `Pop`/`Push` asserts. Pooled prefabs derive from `PoolableMono` (`ResetItem()` hook, `PoolItem` reference). Projectiles (`AbstractProjectile` → `StraightProjectile`/`CurvedProjectile`) and `Bomb` are popped by their skills via `poolManager.Pop<T>(poolItem)` and `Push`ed back themselves; guard against double-push with a `_released` flag as the existing ones do. `AbstractProjectile` ignores only its own `Attacker`, and projectiles/bombs are `IDamageable`, so several spawned from one fish overlap and can hit each other — filter by layer or type before adding multi-shot skills. Editing the pool asset (`Assets/DevLib/ObjectPool/PoolManager.asset`) is a common source of merge conflicts.

**Fish are pooled too.** `Fish` derives from `Agent`, so it cannot use `PoolableMono`; it implements `IPoolable` directly. Rules that break silently or throw if missed:
- `Fish.PoolItem` must be `[field: SerializeField]` and assigned on the **prefab asset** (the pool clones the prefab asset). A non-serialized property is always `null` on the clones and `PoolManagerSO.Push` throws `ArgumentNullException`. `FishSpawner` calls `poolManager.Pop<Fish>(prefab.PoolItem)`, so every fish prefab in a `FishSpawnListSO` needs its own `PoolItemSO`, registered in the manager the scene uses.
- A `PoolManagerSO` asset is initialised only if a scene `PoolInitializer` references **that same asset**. `FishSpawner.poolManager` must point at the one the `PoolInitializer` uses (currently `Assets/DevLib/ObjectPool/Items/_Fish PoolManager.asset`, not `PoolManager.asset`); otherwise `Pop` hits the "must be initialised" assert and a `NullReferenceException`.
- `Pool.Pop` calls `ResetItem()` on every reuse, so `Fish.ResetItem()` must reset everything a fish accumulates (`State`, `IsInSea`, `HasStartedFalling`, `_hasRisen`, `_released`, Rigidbody kinematic/velocity, `LungeModule.ResetLunge()`). Add to it when a fish gains new per-life state.
- `BehaviorGraphAgent` has no `OnEnable`/`OnDisable` handling, so a deactivated fish leaves its graph frozen mid-run. `Fish.OnSpawn` therefore rebinds the state channel and calls `BTAgent.Restart()` on every spawn.
- Return a fish with `Fish.ReleaseToPool()` (idempotent via `_released`, stops the current skill first, falls back to `Destroy` when there is no pool). The graph's `ReleaseFishAction` calls it.
- Known gap: `EnemySkillModule`/skill cooldowns are not reset on reuse, so a recycled fish may start with skills on cooldown.

### Fish (`CHG/02.Script/FishSystem`)
`FishSpawner` picks a prefab from a `FishSpawnListSO` by `Grade` (weighted, optional downgrade), pops it from the pool (`poolManager.Pop<Fish>(prefab.PoolItem)`, see Object pooling), resets its position/rotation, then `Fish.OnSpawn(pullForce, target, poolManager)` writes the `Fish`/`Target` blackboard variables, binds the state channel, restarts the graph (`BTAgent.Restart()`), hands the target to `LungeModule`, and launches the fish via `Rigidbody` using `CoreSystem/PhysicsUtil` (weight-resistance and jump-height helpers). Stats come from `FishDataSO`; the spawner is also fed `RodDataSO.RollGrade()` (per-grade weights) and `PullPower` by the caller. `FishFacingModule` turns the model pivot toward the velocity (the flight velocity while the lunge has the Rigidbody kinematic).

Fish lifecycle: `FishStateEnum` is Jump → Combat → Lunge → Return → Dead. **The Behavior graph decides every transition** (see below); `Fish.State` is only a mirror that `Fish` keeps by subscribing to the `StateChannel` (`HandleStateChanged`), so C# readers such as the knockback gate (`State == Combat` only) see the same value the graph has. There is no `ChangeState` in `Fish` any more; do not add C# calls that set the state. `Fish` supplies facts for the graph instead: `HasStartedFalling` (set in `FixedUpdate` once the fish has risen and its vertical velocity turns non-positive, only while `Jump`), `IsInSea` (a trigger tagged `Sea`; `ConsumeSeaTouch()` clears it), and `IsDead`. The one transition C# sends itself is `Dead`, because death originates outside the graph: `Fish.Dead()` calls `SendState(Dead)`.

Lunge: `LungeModule` owns its own private `Phase` (`Idle`/`Approach`/`Return`) and exposes `IsFlying`, `IsApproaching`, `IsReturning`, `HasLunged` and `IsParryable` (approach phase and within `FishDataSO.ParryRange`); it never touches `Fish.State`. The phase **must be set in `BeginFlight` and returned to `Idle` in `EndFlight`/`ResetLunge`**; a phase that is never set makes the whole module inert, and one that is never cleared makes `Update` re-run `EndFlight` every frame and freeze the fish. `StartLunge()` (once per fish, needs `Target`) sets the Rigidbody kinematic and moves the **Fish root** along a hand-integrated ballistic arc (`PhysicsUtil.SolveBallisticVelocity`/`BallisticPosition`) to a point in front of the player; with no parry it turns around on arrival and flies back to the point where it touched the sea, otherwise a successful parry damages the fish and starts the return at once. On death mid-flight `HandleDeath` calls `EndFlight(true)` (only if `_phase != Idle`), handing back to physics with the current velocity. Lunge and the skill system are independent modules on the same fish; the graph decides which one runs.

### Behavior graph (`CHG/03.GameModule/Fish BT.asset`)
**Read [docs/fish-bt-design.md](docs/fish-bt-design.md) before touching the graph, `Fish.State`, or any BT node.** The user wants the graph built like the course PDFs 06/07: `State` is a `[BlackboardEnum]` enum plus a `StateChannel`; the root is a *Start On Event Message* (Restart) that assigns the message to `State` and restarts `Switch(State)`; **state transitions are `Send Event Message` nodes at the end of a branch card inside the graph**, not C# `ChangeState` calls. C# only supplies facts (`IsInSea`, `IsDead`, `HasStartedFalling`, lunge phase) and may send the channel itself only for events that originate outside the graph (death). The migration to this structure is **done for the fish graph**; what is still open (the death logic, runtime checks) is in section 8 of that doc — keep the checklist there updated. The boss graph uses the same pattern (see Boss below and section 11 of that doc).

Fish AI runs on a Unity Behavior graph executed by the `BehaviorGraphAgent` that `Fish` requires (`[RequireComponent]`); one graph is shared by all fish, and each fish gets its own graph instance. The saved asset has two start points that the editor joins under a top-level *Run in Parallel*:
- `On Start` → `Send "Jump" change on StateChannel` (the initial state, sent as an event).
- `On StateChannel (Restart)` (*Start On Event Message*, mode Restart, `Assign State to` **linked to the blackboard `State`**) → `Switch(State)`. Every message restarts the switch, which ends the running branch and starts the new state's branch:
  - `Jump` → `Repeat` → card [`If HasStartedFalling`, `Send "Combat"`]
  - `Combat` → `Repeat` → *Try In Order* of `Pass If [EscapedToSea] → [Wait 0.5, Release Fish]`, `Pass If [CanLunge] → Send "Lunge"`, `Pass If [NotInSea] → UseSkillAction`. `EscapedToSea` is `IsInSea && (!CanLunge || HasLunged)`, `CanLunge` is `IsInSea && CanLunge && !HasLunged`, so the three branches never compete for one fish state.
  - `Lunge` → *Try In Order* of card [`StartLungeAction`, `Send "Return"`] and a fallback `Send "Combat"` (used when the lunge could not start)
  - `Return` → card [`WaitLungeEndAction`, `Send "Combat"`]
  - `Dead` → card [log, `Release Fish`]; this is the place for the fish's death logic, and it must end with `Release Fish`.
- A skill node that shows a red X in the play-mode debug view has returned `Failure`. For `UseSkillAction` that just means no skill is usable right now (module/skill cooldown, an `AbstractSkillCondition` such as HP-below failing); `Repeat` retries every frame, so this is normal between casts.
- Blackboard variables: `Fish`, `Target`, `State`, `StateChannel`, and the editor's built-in `Self`. `StateChannel` must have **no asset assigned**: an unassigned channel variable gets its own channel instance per graph instance (created in `BehaviorGraph.InitializeInstance`), so fish do not receive each other's messages. `State` is written by the root node from the message, not by C#.
- Code sets blackboard variables by name in `Fish.OnSpawn` (`Fish`, `Target`) and reads the channel with `BTAgent.GetVariable("StateChannel", …)` in `Fish.BindStateChannel`. Names and types must match the graph's blackboard; a mismatch fails silently. `BindStateChannel` compares `channel.Value == null` — that condition once had the sign flipped, which left `Fish.State` stuck on `Jump` and made `SendState(Dead)` a no-op.
- Custom nodes live in `CombatSystem/BT/{Action,Condition,Channel}`. The graph asset references node classes by type and `id`: create nodes from the Behavior editor and don't rename or move them by hand (some are in the global namespace, others under `CHG._02.Script.CombatSystem.BT.*`).
- State-machine rules of this graph (details and reasons in `docs/fish-bt-design.md`): a state branch must either `Repeat` (only `Jump` and `Combat` do) or end with a `Send` of the next state, because *Start On Event Message* just waits for the next message once its child finishes — a branch that neither loops nor sends leaves the fish stuck in that state. Never put a `Repeat` above the `Switch`: it would re-run one-shot branches such as `Dead` every frame. `Switch` picks its branch only when it starts, which is why the restart-on-message root is needed. The `Send Event Message` node transmits one update after it starts, so keep it as the **last** line of a card. Nodes that run for a long time must clean up in `OnEnd`, because a state change or death ends them from outside (`UseSkillAction` calls `StopSkill()` there, guarded by `_started`).
- Semantics that bite: `OnUpdate` only runs if `OnStart` returned `Running` (returning `Success`/`Failure` ends the node immediately). `Repeat` restarts its child every frame after success *or* failure. *Conditional Guard (Modifier)* with no child returns `Failure`. The *Random* node runs exactly one randomly chosen child and returns its result, with no fallback to the others.

### Boss (`CHG/02.Script/BossSystem`, graph `CHG/03.GameModule/Boss BT.asset`)
Same state-channel pattern as the fish; full structure, rules and open items are in section 11 of `docs/fish-bt-design.md`. `Boss : Agent, ISkillEntrySource` (stats, `Skills`, appear/groggy timings and `BreakableSkills` in `BossDataSO`) is spawned with `Boss.OnSpawn(target)` (only `Test/TestBoss.cs` calls it so far), which sets the blackboard `Boss`, `Target`, `AppearDuration`, `GroggyDuration`, binds the `BossStateChannel` and calls `BTAgent.Restart()`.
- `BossStateEnum`: `Appear` → `Combat` ⇄ `Groggy`, → `Dead`. The graph sends `Appear` (On Start) and both returns to `Combat` (after a `Wait`); C# sends only the outside events: `Dead` from `Boss.Dead()`, and `Groggy` from `GroggyModule` when its gauge fills. `Groggy` must come from C# so it can interrupt a running skill: the restart ends `UseSkillAction`, whose `OnEnd` stops the skill. `Boss.State` mirrors the channel.
- `GroggyModule` fills from `OnDamaged` and `AddGroggy(amount)`, only while `State == Combat` and not already full; the graph's `ResetGroggyAction` empties it at the end of `Groggy`.
- `PatternBreakModule`: damage taken while a skill listed in `BossDataSO.BreakableSkills` is running (warning time included) accumulates; at `BreakDamage` it calls `CurrentSkill.StopSkill()` and then `AddGroggy(GroggyAmount)`. It is not a state change; the accumulator resets on `EnemySkillModule.OnSkillEnd`.
- Pitfalls already hit: the *On StateChannel* node must be in **Restart** mode (in Default mode a `Send` from inside the running branch is dropped and the graph stalls after `Appear`); set the blackboard variable `"Boss"`, not the built-in `"Self"` (`GameObject`, so `SetVariableValue` silently ignores a `Boss`).

## Conventions

- Data is ScriptableObject-driven (`[CreateAssetMenu]` under `Fish/...` or `Lib/...` menus); events between decoupled systems go through `EventChannelSO` with `GameEvent` subclasses.
- Unity `.meta` files are committed — always move/rename assets through git together with their `.meta`, and never delete a `.meta` alone.
- The project is Input System only (`activeInputHandler: 1`): use `Keyboard.current`/input actions, never `UnityEngine.Input` (it throws at runtime).
- With the Editor open, compile errors and runtime exceptions are readable from `%LOCALAPPDATA%\Unity\Editor\Editor.log`; this is the only text log since there is no CLI build.
