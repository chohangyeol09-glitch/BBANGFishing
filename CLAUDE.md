# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BBANGFishing is a Unity 6 (`6000.3.10f1`) fishing game using the Input System, Cinemachine and TextMesh Pro. It is a team project developed on per-member branches (`CHG`, `KU`, `NKT`, `JJK`, `Base`, merged into `main`). Code comments, tooltips and log messages are written in Korean; keep new ones consistent with that.

There is no CLI build, lint or test setup: no `com.unity.test-framework` package, no test assemblies, no CI config. Compiling, running and testing all happen in the Unity Editor (scenes such as `Assets/Member/CHG/01.Scene/TestScene.unity` are used as sandboxes). `*.csproj`/`.sln` files at the root are generated by Unity/Rider and should not be hand-edited.

## Layout and ownership

- `Assets/DevLib/` — shared, reusable systems, each in its own asmdef (ModuleSystem, SkillSystem, ObjectPool, SoundSystem, EventChannelSystem, AnimatorSystem, DatabaseSystem). **Shared across team members — don't modify these to suit one feature; layer new behavior on top from a member folder.** Namespaces are `DevLib.<System>`.
- `Assets/Member/<initials>/` — per-person work areas (`CHG`, `KU`, `NKT`). Stay inside the area you're working for. CHG code lives under `Assets/Member/CHG/02.Script/` with namespace `CHG._02.Script.<Folder>`; NKT uses `NKT.<Folder>`.
- Member scripts have **no asmdef** (they compile into `Assembly-CSharp`), so they can reference every DevLib assembly. DevLib asmdefs cannot reference member code, and `ModuleSystem`/`PoolRuntime` have no dependencies of their own — keep it that way.

## Architecture

### Module system (`DevLib/ModuleSystem`)
The core composition pattern. A `ModuleOwner` (e.g. `Agent` → `Fish`, NKT `Player`) collects every `IModule` found via `GetComponentsInChildren` in `Awake`, keys them **by concrete type** in a dictionary, then calls `Initialize(owner)` on all, then `IAfterInitModule.AfterInit()` on all.

- Only one module of each concrete type per owner (`ToDictionary` throws on duplicates); `GetModule<T>()` also resolves by interface/base type.
- `Initialize` order is not guaranteed: in `Initialize` only grab references (`owner.GetModule<X>()`); subscribe to other modules' events in `AfterInit`.
- Derive from `Module` for the `_owner` boilerplate, or implement `IModule` directly when a base class is already taken (the enemy skill modules do this).

### Combat (`CHG/02.Script/CombatSystem`)
- `IDamageable` + `DamageData` struct are the shared damage contract. `Agent` (`Agents/Agent.cs`) is the abstract `ModuleOwner` + `IDamageable` base with health/death events; `Fish` extends it. Projectiles and bombs are also `IDamageable` so they can be shot down.
- **Enemy skill system is CHG's own, separate from `DevLib/SkillSystem`** (which is player-oriented: `AbstractSkill`/`AbstractSkillModule`/`SkillDataSo`). Do not make `AbstractEnemySkill` inherit from it. Two layers:
  - *Execution* — `AbstractEnemySkill` (MonoBehaviour; runs `WarningTime` telegraph then the abstract `ExecuteSkill` coroutine, owns per-skill cooldown) driven by `EnemySkillModule` (one skill at a time, plus a module-level cooldown with per-skill `moduleCoolTimeOffset` / `ignoreModuleCoolTime`). Concrete skills are in `EnemySkillSystem/Skills/`; skills must be child objects of the module's GameObject and are keyed by `EnemySkillDataSO.SkillIdHash.HashValue` (must be unique per owner).
  - *Selection* — `ISkillStrategy.SelectNextSkillId(SkillStrategyContext)` picks what to use next; `PrioritySkillStrategySO` is the only implementation (highest priority group first, random among usable entries, optional HP% condition). `AttackDecisionModule` runs the strategy on every skill end and each frame while idle, after `startDelay`, and needs its `Target` set (`FishSpawner` assigns it on spawn).
- Planned but not yet implemented (from the design notes): `BossPhaseModule` (swap strategy by HP threshold), a second `AbstractSkillModule`-style track for boss auras, and a boss-only `BossWeakPoint` interrupt component. Deliberately **not** adding weak-point fields to the shared `DamageData`.
- Skills are identified everywhere by `HashDataSO` (from `DevLib/AnimatorSystem`, a ScriptableObject wrapping `Animator.StringToHash`), used for both skill IDs and animator params.

### Object pooling (`DevLib/ObjectPool`)
`PoolManagerSO` holds `PoolItemSO` entries and is initialised at runtime by a scene `PoolInitializer` (singleton, `DontDestroyOnLoad`) — a scene without one will trip the `Pop`/`Push` asserts. Pooled prefabs derive from `PoolableMono` (`ResetItem()` hook, `PoolItem` reference). Projectiles (`AbstractProjectile` → `StraightProjectile`/`CurvedProjectile`) and `Bomb` are popped by their skills via `poolManager.Pop<T>(poolItem)` and `Push`ed back themselves; guard against double-push with a `_released` flag as the existing ones do. Editing the pool asset (`Assets/DevLib/ObjectPool/PoolManager.asset`) is a common source of merge conflicts.

### Fish (`CHG/02.Script/FishSystem`)
`FishSpawner` picks a prefab from a `FishSpawnListSO` by `Grade` (weighted, optional downgrade), instantiates it, wires the `AttackDecisionModule` target, then `Fish.OnSpawn(pullForce)` launches it via `Rigidbody` using `CoreSystem/PhysicsUtil` (weight-resistance and jump-height helpers). Stats come from `FishDataSO`.

## Conventions

- Data is ScriptableObject-driven (`[CreateAssetMenu]` under `Fish/...` or `Lib/...` menus); events between decoupled systems go through `EventChannelSO` with `GameEvent` subclasses.
- Unity `.meta` files are committed — always move/rename assets through git together with their `.meta`, and never delete a `.meta` alone.
